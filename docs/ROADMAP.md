# 공개 개발 로드맵

이 문서는 SEA Ops Arena **공개판 자체**의 개발 방향을 설명합니다. SEA 또는 다른 비공개 시스템의 내부 개발 로드맵은 포함하지 않습니다.

## 현재 — v0.6

공개 벤치마크의 실행·비교·반복 평가·재현에 더해, 실제 외부 baseline을 오염 없이 받을 수 있도록 **정답 비노출 입력과 공개 과제 조건을 하나의 입력팩으로 고정**했습니다.

현재 구현 범위:

- 공개 요청·최종 판단 결과 계약
- 외부 시스템 연결용 최소 인터페이스
- 합성 실행 환경
- 4개 업무 영역, 12개 공개 합성 사례
- 판단 일치율 / 불필요 실행 / 필요한 실행 누락 / 실행 성공률
- 여러 판단 결과의 동일 조건 비교
- 반복 판단 안정성 집계
- Markdown / JSON 보고서
- 재현 가능한 실행 결과 묶음
- request ID 커버리지 검사
- 허용 필드 기반 `public-decision-set-v1`
- 평가 정답·태그를 제거하는 `arena-input-pack-v2`
- 입력팩 내부의 공개 과제 정의와 상태 의미
- 입력팩 내부의 text-only / no-tools baseline 실행 제약
- 공식 frozen 입력팩과 SHA-256 고정
- 실제 결과의 `suite_sha256` 결합
- 실제 결과의 `input_pack_sha256` 결합
- 실제 결과 평가 시 입력팩 전체 재검증
- 원본 로그를 복사하지 않는 공개 결과 템플릿
- 실제 결과가 참조하는 입력팩의 저장소 존재 여부 감사
- 첫 실제 모델 baseline을 위한 공개 반복 프로토콜
- 예상 밖 결과를 즉시 실패로 확정하지 않는 결과 유효성 검토 원칙
- 주요 CLI 경로를 포함한 GitHub Actions 자동 검증

현재 저장소에 포함된 결과는 **합성 fixture**이며 실제 모델 또는 SEA 성능 결과가 아닙니다.

## 다음 — 첫 실제 외부 baseline 결과

다음 단계는 새로운 내부 구현을 공개하는 것이 아니라, 확정된 공개 경계를 사용해 실제 외부 모델 결과를 올바른 절차로 처음 축적하는 것입니다.

실험 절차는 [`BASELINE_PROTOCOL.md`](BASELINE_PROTOCOL.md)를 기준으로 합니다.

핵심 순서:

1. 공개 평가용 시나리오와 공식 frozen 입력팩을 고정합니다.
2. 모델에는 해당 입력팩만 제공합니다.
3. 외부 검색·RAG·도구 없이 새 실행으로 판단을 생성합니다.
4. 모델 호출과 원본 로그는 별도 환경에서 관리합니다.
5. 시나리오 해시와 입력팩 해시를 검증합니다.
6. 동일 모델·버전·입력팩으로 최소 3회 반복합니다.
7. 기대값과 다른 결과나 실행 이상이 나오면 곧바로 실패로 확정하지 않고 유효성을 검토합니다.
8. 입력 전달·실행 조건·파싱 문제라면 무효 실행으로 분류하고 baseline 집계에서 제외합니다.
9. 시나리오·기대값·평가 기준의 결함이라면 벤치마크 버전을 갱신하고 새 버전에서 다시 평가합니다.
10. 유효성 검토를 통과한 결과만 `sea-ops-arena-template` 기반 최소 공개 결과로 정리합니다.
11. 같은 조건의 유효 실행 중 유리한 결과만 임의로 선택하지 않고 정해진 반복 단위로 함께 평가합니다.
12. 공개 감사와 별도 의미 단위 유출 검토를 통과한 최종 결과만 저장소에 추가합니다.

첫 실제 결과에서는 모델 수를 늘리는 것보다 **실험 입력과 조건, 그리고 결과 자체의 유효성이 확인되었음**을 우선합니다.

## 이후 — baseline 비교 확대

첫 실제 결과 절차가 안정화되면 같은 입력팩으로 여러 공개 모델 또는 외부 시스템 결과를 비교합니다.

비교 시 유지할 조건:

- 동일한 평가용 시나리오 파일
- 동일한 frozen 입력팩
- 동일한 공개 과제와 no-tools 조건
- 공개 가능한 모델명과 버전
- 반복 횟수 기록
- 같은 공개 지표 계산
- 동일한 결과 유효성 기준 적용
- 유효 실행만 비교 대상으로 사용

Arena는 임의의 가중 종합 순위를 만들지 않고 원래 관찰값을 공개하는 방향을 유지합니다.

## 이후 — 시나리오 확장

현재 12개 합성 사례를 기반으로 공개 문제의 폭을 넓힙니다.

후보 범위:

- 시간 순서가 중요한 요청
- 연속된 여러 작업
- 실행 실패가 포함된 사례
- 여러 요청 사이의 공개 충돌
- 서로 다른 업무 영역을 잇는 합성 사례
- 동일 문제의 난이도 변형

추가 시나리오도 특정 비공개 정책이나 내부 구조를 복제하지 않고, 외부에서 문제와 기대값을 독립적으로 이해할 수 있는 합성 사례로 작성합니다.

새 시나리오에서 예상 밖 결과가 반복될 경우 연결 시스템만 의심하지 않고 **문제의 명확성, 정보 충분성, 기대값과 평가 기준도 함께 검토**합니다.

## 이후 — 공개 결과 시각화

코드를 읽지 않는 사람도 결과를 이해할 수 있도록 정적 리포트와 간단한 시각화를 추가합니다.

우선순위:

- 어떤 시나리오와 입력팩을 사용했는지
- 어떤 검토 완료 결과 파일을 평가했는지
- 반복마다 얼마나 달라졌는지
- 불필요 실행과 필요한 실행 누락이 어디서 발생했는지
- 같은 입력으로 결과를 다시 확인할 수 있는지

디버깅 과정이나 무효 실행을 전시하는 것이 목적은 아닙니다. 공개 결과 화면은 **유효성 검토가 끝난 결과를 명확하고 간결하게 보여 주는 것**을 우선합니다.

## 유지되는 원칙

1. 공개 벤치마크는 독립적으로 재현 가능해야 합니다.
2. 실제 결과와 합성 fixture를 명확히 구분합니다.
3. 실제 판단 생성에는 평가 정답을 제공하지 않습니다.
4. 실제 baseline 입력과 공개 과제 조건을 함께 고정합니다.
5. 결과 불일치는 즉시 시스템 실패로 확정하지 않고 실행과 벤치마크 양쪽을 검토합니다.
6. 무효 실행은 최종 baseline 집계에 포함하지 않습니다.
7. 벤치마크 결함이 확인되면 버전을 갱신한 뒤 다시 평가합니다.
8. 유효성 검토를 통과한 결과 중 유리한 실행만 골라 결과를 왜곡하지 않습니다.
9. 공개 지표의 계산 방법은 설명할 수 있어야 합니다.
10. 외부 시스템의 비공개 내부 구현을 공개 벤치마크에 복제하지 않습니다.
11. 비공개 저장소의 Git 이력이나 내부 자료를 공개 저장소로 가져오지 않습니다.
12. 여러 공개 파일을 조합했을 때 비공개 구조를 역추론할 수 있는 정보도 공개하지 않습니다.
13. 원본 로그를 깎아 공개하지 않고 허용 필드 템플릿에 필요한 값만 옮깁니다.
14. 실제 결과는 평가용 시나리오와 정답 비노출 입력팩 모두에 해시로 결합합니다.
